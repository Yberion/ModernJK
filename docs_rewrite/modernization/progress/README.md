## Working practices (keep them)

- Language: answers in French, short; everything persisted (docs, comments, commits) in English, full sentences. Never mention the earlier proof-of-concept code base.
- Commits are made by hand, never by Claude: give a Conventional Commits title with the step first, for example `feat(netcodec): step 6, ...`; do not stage files. If a commit is ever made here, signing needs `git -c gpg.program=C:/Logiciels/GnuPG/bin/gpg.exe commit ...` (the key is in Gpg4win; Git Bash's own `gpg` has none; the passphrase prompt opens in a window).
- C++: C++20 inside netcodec, C++ Core Guidelines (named casts, `noexcept`, `[[nodiscard]]`, `constexpr`, `std::span`, RAII, initialised members), unsigned arithmetic for bit manipulation; strict warnings as errors (top-level project); clang-tidy at zero (`mingw-clang-tidy` preset); no exceptions. Comments describe the format and the code, never the Python prototype.
- Validations (10 November 2026): a change of the library (`codemp/netcodec`) gets the full VM validations (`validate.sh`, `validate.bat`, which also build the game); a change of the engine only (`codemp/server`, `codemp/client`, ...) gets only the game build (`cmake --build Z:\ModernJK\build-modernjk\msvc-x64 --config Release`, and on the Linux VM `build-modernjk/gcc-ded`, plus `gcc-mp` when client files change), then the install.
- Every change: build and run the golden tests on several presets (Release, Debug with index checks, x86, ASan + UBSan), then the benchmarks; a cleanup must show no performance regression. Compare timings with the legacy timings of the same run (this machine varies by up to 8 % between runs). Changes of a few percent are only visible in the warm timing (fastest of 5 codings per message) of step 6 part C, A/B against a build of the previous commit; the cold benchmark is memory-bound and varies by up to 9 %, more while a game runs on the machine.
- GCC is built and timed only on the Linux VM, never on the Windows machine (a portable GCC there was too slow and was stopped, and it does not reproduce the Linux timings); this machine builds with llvm-mingw clang only.
- GCC-only warnings exist (`-Wuseless-cast` on 32 / 64-bit size types: use `ToU32`); MSVC is stricter on old engine code (the legacy benchmark is built in C++11 without the project settings).
- Mod compatibility is never a criterion and never a question to ask; no loss of precision; as few settings as possible.
- Timing of the client packets (10 November 2026): the A/B scripts take `BENCH=client` (`ab_clang.sh`, `ab_gcc.sh`) or `ABM_BENCH=client` (`ab_msvc.bat`) to time `netcodec_bench_client` on the recorded sessions instead of `bench_codec` (`ab_client.awk` turns its output into the summary's lines).
- Timing (7 November 2026): GCC on Linux is the server target (about 95 % of servers) and has more weight than MSVC for encoder changes; every encoder or decoder change gets an alternated A/B against the previous commit with clang here (`codemp/netcodec/scripts/ab_clang.sh`, only while the machine is quiet: ask first) and with GCC on the Linux VM (`codemp/netcodec/scripts/ab_gcc.sh`, aligned code; GCC 12 until 16 November 2026, GCC 15 since); MSVC with `codemp\netcodec\scripts\ab_msvc.bat` when it matters (if the VM has no git, run `bash codemp/netcodec/scripts/ab_msvc_ref.sh` here first; the script refuses a stale reference); GCC 16.2 (`ab_gcc_podman.sh`) in the final measurements. Tools and profiler: [step-06-cpp-codec.md](step-06-cpp-codec.md), part C, "Timing and profiling tools".
- The VM logs are in the shared folder (`build-netcodec/validate-linux.log`, `validate-windows.log`): read them directly; only the summary is pasted. A validation run during which a netcodec source changed now ends with a FAIL line (it tested a mix); the A/B summaries warn when the machine was busy (legacy coder moving by more than 4 %): then run again.
- Test hashes: `netcodec_ROUNDTRIP_HASH`, `netcodec_SYNTHETIC_HASH`, `netcodec_CLIENT_ROUNDTRIP_HASH` and `netcodec_CLIENT_SYNTHETIC_HASH` in `test/CMakeLists.txt` change with the format, the tables or the generator (update them from clang Release, then every preset and both VMs must agree); `angle_hash.py` gives the determinism test's constant.
- Every change of the branch against OpenJK (engine, game, cgame, settings, behaviour) is also described in [../CHANGES.md](../CHANGES.md), in plain words and tables, with its reason and what it implies (9 November 2026). Since 14 November 2026 that page has one section per change, always in the same order (Before, Now, Why, Gain, then the technical details folded) and a line in the summary's list of changes; a change that moves a delay also updates the summary's "Delays before and now", with the measure; no technique in the summary.
- Game measurements with bots (step 14, 11 November 2026): `gamestats` with `docs_rewrite/modernization/tools/gamestats/` (`gamestats_windows.sh` here, under lldb, with `gamestats_agg.py`; `gamestats.sh` and `gamestats_table.py` on Linux). Since 12 November 2026 the proof is the scripted scenarios (`SCENARIO=`, `gamestats_scn.py`; How to resume, point 4): the same module at `sv_fps` 20 is the reference, compared count by count, no batch noise. For free-for-all benches, rules learnt the hard way: the reference (until 11 November OpenJK's saber at 20 Hz, the module of the worktree `E:\Git\jka\OpenJK_Netcode_saberref`, built in its `build-clang` here and `build-ref-gcc` on the VM; now the same module at `sv_fps` 20) runs in every batch next to the configurations tested, never compared across batches (results move by up to 15 % from one batch to another); 12 servers per configuration and 3 batches (180 server-minutes) give about ±3 %; the bots always with `bot_debugClientRate 1` (removed on 12 November 2026: the bots now always send a command per tick); each configuration passed as one argument (a bash array, never an unquoted list: split at its spaces it lost its cvars); the fast mode (`FAST=1`: `fixedtime` and `timedemo`) is valid and about 8 times real time per core; damage and blocks per minute depend on the fights' dynamics, so a damage coefficient moves them less than its own change. Linux game measurements run on the VPS (1 vCPU, 2 GB, no live server; `FAST=1`, 4 servers at a time), never on the Linux VM, which only builds. The dedicated server also reads the `modernjk_server.cfg` of its base path, so the scripts set the test servers' settings themselves (sabers only, force jump and saber skills only: `g_forcePowerDisable 163837`, no saber locks, no private duels); `PREMAP` sets latched cvars before the map, for example `PREMAP="g_forcePowerDisable 0"` for the force powers. The bots use no force power at all unless `g_forcePowerDisable` is 0, and never grip. Without `SEED`, a run's free play depends on the machine's load (the first frames of the map follow the real time): give `SEED=<n>` to reproduce a run or to scan free plays (12 November 2026).
- Checks in game (11 November 2026): short, 30 s to 1 min per check; the statistics commands (`svnetstats`, `netstats`) are the measure; derive rates from the counts (packets per snapshot, 20 snapshots per second) rather than asking for timed sessions.
- Settings (step 11): a value that needs no measuring is a constant, without a cvar; debug cvars exist only for computed values and are `CVAR_CHEAT` on the client; what must not be bypassed is enforced on the server. Removing a field from a game-module table indexed by position (such as `userinfoFields` and the bit mask `g_userinfoValidate`) moves the bits after it: change the default and say how to reset stored values.
- Before proposing options, survey what recent games do when it is a design question (10 November 2026: network-settings.md), with sources labelled primary, secondary or community.
- Designs follow recent games and libraries, not what exists in the JKA community (11 November 2026): the JKA mods only tell which game code a change touches; a modern, well-thought design is wanted even if it means starting again from zero.
- Math and random numbers (12 November 2026): the code calls only the entry points `shared/qcommon/q_libm.h` (`Q_sinf`, `Q_sin`, `Q_sqrtf`, `Q_atof`, `Q_ScanFloats`, ...) and `shared/qcommon/q_rand.h` (`Q_irand`, `Q_flrand`, `Q_RandInt` on a `qrand_t`, ...), never the C library's math functions, `atof`, `sscanf %f` or `rand()`; a new call of these is a bug (it brings platform differences back). Two random draws must never sit in one call's arguments or as operands of one operator: `tools/rng/unsequenced.py <dirs>` lists such statements (none in the game).
- When a cvar is removed, the behaviour left is the one of its default value (12 November 2026: `cg_smoothCamera` went with the damping of 0, the default).
- Patching files from scripts: write the Python script with the Write tool and run it with `python -I` (Git Bash heredocs mangle `\n` and backslashes); read with `read_bytes().decode("utf-8")` and write with `write_bytes(s.encode("utf-8"))`, which keeps LF (and CRLF for `.bat`, which must stay CRLF). Never `read_text()`: on Windows it decodes as cp1252, and writing the result back as UTF-8 double-encodes every non-ASCII character (it happened on 10 November 2026 to four documents, repaired the same day; a check: no run of characters that encodes as cp1252 and then decodes as UTF-8). Console output of Git Bash and of Python can show correct UTF-8 as mojibake and the reverse: check the bytes, not the display. `python -I` ignores `PYTHONIOENCODING`: a script that prints non-ASCII text calls `sys.stdout.reconfigure(encoding="utf-8")`.
- No attributions in persisted text (15 November 2026): documents, comments and commit titles never say who decided or asked; a decision is written with its date ("Choice (10 November 2026): 1a", "decided on 5 November 2026"), the roles neutrally ("the development machine", "the validations run on the VMs").
- Status marks (16 November 2026): every status carries an emoji, ✅ done, ⏳ in progress or planned (to do, later, set aside), ❌ cancelled or dropped, in the status tables, the headings of PLAN.md and the parts lists.
- Decisions are put all at once (15 November 2026): every open decision of a step in one message, each with the problem in a sentence, its options, their advantages, drawbacks and costs (CPU, bytes, memory, delay at each frame rate), what replaces what is removed, and the documented practice of the library or of recent games first.

## Known issues found on the way (not fixed)

- Single player: the mouse does not move the view in game, while it works in the menus (MSVC x64 build, 16 November 2026; single player had not been run before step 17, which changed none of the input code). Left for after plan step 15 (the input on SDL 3), looked at then if it remains.

- LLVM libc on 32-bit x86 with GCC, Clang 14 and MSVC: its square root falls back to software (`asinf`, `acosf`, `acos`, `rsqrtf` 70 to 300 ns), the same bits; 32-bit is not a target ([../surveys/deterministic-math.md](../surveys/deterministic-math.md) section 10).

- `PM_irand_timesync`'s numbers come from the command's time, which the client chooses within what the server accepts: a modified client could pick times giving favourable saber draws, as with 1.01 and with Source's per-command seed ([../surveys/random-numbers.md](../surveys/random-numbers.md) section 6).

- Upstream OpenJK: the UCRT's `strtof` and `sscanf %f` read a decimal exactly halfway between two floats differently from glibc (`16777217`); fixed on this branch by the entry point's parser.

- Upstream OpenJK: the Linux `Sys_Milliseconds` (`shared/sys/sys_unix.cpp`) reads `gettimeofday`, the wall clock: a step of the system time stops the server's frames (clock going back) or runs up to 5 s of them at once (going forward). Fixed on this branch on 12 November 2026 (`clock_gettime( CLOCK_MONOTONIC )`; [../CHANGES.md](../CHANGES.md) section 23).

- Upstream OpenJK and its forks (TaystJK checked): `Sys_SnapVector` rounds ties away from zero with MSVC and to even elsewhere (prediction misses of up to 2.7 units between a Windows client and a Linux server), and `SnapVector` truncates except with MSVC x86. Fixed on this branch; the code of 1.01, OpenJK and the fix compared side by side, with compatibility and test results, for a merge request upstream: [step-06-cpp-codec.md](step-06-cpp-codec.md), part F, "Code comparison".

- Legacy client (`CL_ParseSnapshot`, `codemp/client/cl_parse.cpp`): when the old snapshot had no vehicle, the server deltas the vehicle player state from nothing (`MSG_WriteDeltaPlayerstate(msg, NULL, &frame->vps, qtrue)`) but the client deltas it from `old->vps`. Seen while writing the legacy benchmark; not tested (the benchmark follows the server and the client as written and found no failure on the recordings).


- The `user*` mod fields are networked 1 bit wide, floats included: only the lowest bit reaches the client unless a mod widens them with the overrides files ([../study/02-engine-code-findings.md](../study/02-engine-code-findings.md) section 2.2).

- With `sv_ratePolicy 2` and `sv_maxRate 0`, the client rate became 0 and `SV_RateMsec` divided by zero (read only, not tested). Gone on this branch since step 11 removed the rate policies; upstream OpenJK still has it.
